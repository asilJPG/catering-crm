# Подключение Supabase

Без `.env` CRM работает в демо-режиме: данные и пользователи хранятся в браузере.
Чтобы перейти на настоящую базу:

1. **Проект.** Создайте проект на supabase.com.
2. **Схема.** SQL Editor → вставьте `supabase/schema.sql` → Run. Он создаёт таблицы, права доступа
   (менеджер видит только свои мероприятия, каталог для него только на чтение) и функции склада.
3. **Регистрацию отключите.** Authentication → Sign In / Providers → выключите «Allow new users to sign up».
   Пользователей создаёт только администратор.
4. **Секрет сервера.** Придумайте длинную случайную строку и сохраните её как секрет функций:
   ```bash
   supabase secrets set PASSWORD_PEPPER=<длинная случайная строка>
   ```
   Она нужна, чтобы хеши паролей в базе нельзя было использовать для подбора.
5. **Первый администратор.** Authentication → Users → Add user: email `admin@luma-crm.app`, пароль
   не короче 8 символов, «Auto Confirm User». Затем впишите этот пароль и ту же строку
   `PASSWORD_PEPPER` в `supabase/seed.sql` и выполните его.
6. **Функции.** Через Supabase CLI:
   ```bash
   supabase login
   supabase link --project-ref <ref проекта>
   supabase functions deploy admin-users
   supabase functions deploy password-login --no-verify-jwt
   ```
   `password-login` открыта без токена — она и выдаёт сессию по паролю. Ключ service role функции
   получают сами, в браузер он не попадает.
7. **Ключи в приложении.** Скопируйте `.env.example` в `.env`, впишите адрес проекта и anon-ключ
   (Project Settings → API) и перезапустите `npm run dev`.
8. **Данные.** Каталог и комплекты в базе пустые. Войдите администратором и добавьте позиции
   и комплекты в разделе «Каталог».

## Как устроены права

| Роль | Мероприятия | Каталог и комплекты | Клиенты | Сотрудники |
| --- | --- | --- | --- | --- |
| Менеджер | только свои | просмотр и остатки | просмотр, добавление | — |
| Директор | все | просмотр и правка | просмотр и правка | — |
| Администратор | все | просмотр и правка | просмотр и правка | создание, пароли, отключение |

Права проверяет сама база (RLS), интерфейс их только отражает. Менеджер видит остатки склада
с учётом чужих мероприятий через функцию `get_reservations`, а акт возврата списывает недостающее через
`apply_return_act` — прямого доступа к каталогу у него нет.

Вход идёт по одному паролю. Пароль у каждого сотрудника свой и не повторяется, не короче 8 символов.
Сервер находит владельца по хешу пароля (с секретом `PASSWORD_PEPPER`) и после 8 неудачных попыток
с одного адреса блокирует вход на 10 минут. Внутри Supabase у каждого есть служебный email, пользователи
его не видят.
