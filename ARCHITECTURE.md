# Архитектура Luma Catering CRM

Документ для агента или разработчика, который продолжает работу. Что сделано, как устроено, где подводные камни и что осталось.

## Что это

Внутренняя CRM для кейтеринга (не лендинг). Сотрудники принимают заявки, собирают мероприятия из блюд, мебели, посуды и персонала, считают смету, следят за складом и сдают акты возврата. Интерфейс на русском, валюта — **сум** (`CURRENCY` в `src/lib/format.ts`).

- **Стек:** React 19, TypeScript, Vite 8, react-router-dom 7, дизайн-система **Astryx** (`@astryxdesign/core`, тема `theme-neutral`, светлый режим принудительно), иконки `@heroicons/react`, `convex`.
- **Прод-демо:** https://catering-crm-two.vercel.app (Vercel, проект `catering-crm`, автодеплой из `main` репозитория `asilJPG/catering-crm`).
- **Состояние:** база — **Convex** (облако, регион `eu-west-1`, проект `lokma`, dev-деплой `avid-ladybug-515`). Схема и функции загружены, серверная логика проверена автотестом против живой базы (36 проверок). Без `VITE_CONVEX_URL` приложение работает в **демо-режиме** (данные и пользователи в `localStorage`) — так сейчас работает публичная демо на Vercel. **Production-деплой Convex и подключение Vercel к нему ещё не сделаны** (см. «Долги»).

## Запуск и проверка

```bash
npm install
npm run dev        # http://localhost:5173
npm run build      # tsc -b && vite build
npx oxlint         # есть несколько известных предупреждений, не ошибки
npx convex dev     # в отдельном терминале: следит за convex/ и заливает функции в dev-деплой
```

Если в `.env.local` есть `VITE_CONVEX_URL`, приложение работает на Convex и вход по паролям из базы. Без неё — демо-режим с паролями `admin123`, `director123`, `alisher123`, `dilshod123` (зашиты в `src/lib/backend/local.ts`, на экране входа не показываются).

`.env.local` создаёт `npx convex dev` (там же `CONVEX_DEPLOYMENT`); файл в `.gitignore`.

Автотестов в репозитории нет. Серверную логику проверяли одноразовым скриптом против живой базы, интерфейс — вручную в браузере (см. «Проверенные сценарии»).

## Слой данных

Главная идея: **UI не знает, где лежат данные.** Всё идёт через интерфейс `Backend` (`src/lib/backend/types.ts`):

```
getSession / signIn(password) / signOut
loadSnapshot(user) -> {db, reservations, people}
subscribe?(onChange)            // живые обновления (только Convex)
upsert(collection, row) / remove(collection, id)
applyReturnAct(eventId, act)    // закрывает мероприятие и списывает недостающее — одной операцией
listPeople / createUser / updateUser / deleteUser
```

`src/lib/backend/index.ts` берёт `convex`, если задан `VITE_CONVEX_URL`, иначе `local`. Клиент Convex — «голый» `ConvexClient` (без React-провайдера): токен сессии передаётся аргументом в каждую функцию.

### Store (`src/lib/store.tsx`)

- Держит `Database` в `useState`; действия (`saveEvent`, `saveKit`…) меняют состояние **оптимистично**.
- **Синхронизация обобщённая:** эффект сравнивает прошлое и новое состояние по ссылкам на строки (`diff`) и ставит `upsert/remove` в очередь (цепочка промисов, порядок сохранён). Новое поле работает без нового кода синхронизации, если строку меняют иммутабельно.
- Менеджер **не пишет** `catalog` и `kits` (их пропускает `diff`); сервер всё равно отклонит такую запись.
- **Сервер — источник правды.** Когда очередь записей опустела (успешно или с ошибкой), store перечитывает снимок и заменяет локальное состояние. Если сервер отклонил запись (нехватка склада, нет прав), локальная правка откатывается, а текст ошибки показывается баннером (`syncError`).
- **Живые обновления:** `backend.subscribe` присылает свежий снимок при любом изменении данных у коллег; пока есть неотправленные правки, снимок не применяется (потом всё равно будет перечитан).
- `saveReturnAct` не оптимистичен: вызывает `backend.applyReturnAct` и перечитывает данные.

### Фильтрация по ролям

Сервер отдаёт менеджеру в `snapshot.db.events` только его мероприятия (`createdBy`). Остальные коллекции — целиком. **`reservations`** — занятость склада **всеми** подтверждёнными мероприятиями (включая чужие) без их содержимого. Для локального режима `store.tsx` дополнительно фильтрует `events` по `createdBy`. Любая математика склада на клиенте использует `reservations`, а не `events`.

## Доменная модель (`src/lib/types.ts`)

| Тип | Суть |
| --- | --- |
| `CatalogItem` | `kind`: `dish` / `furniture` / `equipment` / `service`; `stock: number \| null` — число для мебели и посуды, `null` для блюд и услуг (склад не считается); `image` — data URL |
| `Kit` | комплект мебели: `items: {itemId, qty}[]`, цена = сумма позиций |
| `CateringEvent` | `lines: {itemId, qty}[]`, `date`/`endDate` (диапазон занятости), `status`, `createdBy`, `responsible`, `kits` (сколько комплектов выбрано), `returnAct` |
| `ReturnAct` | ответственный, дата, строки `{issued, returned, note}` |
| `Order` | заявка; при создании мероприятия получает статус `converted` |
| `Reservation` | `{eventId, itemId, qty, date, endDate}` — производная, не хранится |
| `AppUser` / `Role` | `admin` / `director` / `manager` |

Статусы мероприятия: `draft`, `confirmed`, `in_progress`, `done`, `cancelled`.

## Склад (ключевая логика, `src/lib/format.ts`)

- **Занимают склад только** `confirmed` и `in_progress` (`RESERVING_STATUSES`). Черновик и отменённое — нет. `done` освобождает.
- Диапазон занятости: `date` … `eventEnd(event)` **включительно** (`endDate`, если не задан — равен `date`). Время суток не учитывается.
- `freeStock(item, reservations, start, end, excludeEventId)` = `stock` минус **самый загруженный день** периода среди чужих подтверждённых мероприятий.
- `shortagesFor(event, reservations, catalog)` — список нехваток; подтвердить мероприятие с нехваткой **нельзя** (диалог в `EventDetail`, блок в `EventWizard`).
- **Комплект** при выборе раскладывается на обычные позиции в `event.lines` (`setKitQty` в `EventWizard`), поэтому склад работает по позициям. `event.kits` хранит только «сколько комплектов выбрано» для отображения.
- **Акт возврата** (`saveReturnAct`): недостающее = `issued - returned` уменьшает `catalog.stock`, мероприятие становится `done`, повторно акт не применяется.

## Роли (`src/lib/permissions.ts`)

| | Мероприятия | Каталог и комплекты | Клиенты | Заявки | Сотрудники |
| --- | --- | --- | --- | --- | --- |
| manager | только свои | чтение + остатки | чтение + **добавление** | все | — |
| director | все | правка | правка | все | — |
| admin | все | правка | правка | все | создание, пароли, отключение |

Принятые решения, не заданные владельцем явно: менеджер может **добавлять** клиентов (иначе не оформит мероприятие); заявки видят все роли. Админ создаёт только менеджеров и директоров.

Права проверяются **дважды**: в интерфейсе (`useCurrentUser().can`, скрытие кнопок, редирект на `/` в `App.tsx`) и на сервере Convex (`convex/data.ts`, `convex/auth.ts`). Интерфейс — удобство, а не защита: в локальном режиме защиты нет вообще.

## Вход и пользователи

- **Вход только по паролю** (логина в интерфейсе нет). Пароль уникален у каждого сотрудника, минимум 8 символов (`MIN_PASSWORD_LENGTH`).
- **Convex:** `users.passHash = HMAC-SHA256(PASSWORD_PEPPER, пароль)`, индекс `by_passHash`. `authNode.signIn` (Node-действие) считает хеш, внутренняя мутация `auth.startSession` находит владельца и открывает сессию (`sessions`, токен 256 бит, 30 дней). Токен лежит в `localStorage` (`luma-convex-token`) и передаётся аргументом в каждый вызов. Секрет `PASSWORD_PEPPER` задаётся командой `npx convex env set` и в репозиторий не попадает.
- **Защита от перебора:** `loginAttempts`; 8 неудач за 10 минут с одного устройства (`deviceId` из `localStorage`) или 40 всего — блокировка. IP в Convex-функциях недоступен, поэтому общий лимит позволяет злоумышленнику временно заблокировать вход всем — осознанный компромисс.
- **Управление сотрудниками** (`authNode.createUser/updateUser`, `auth.deleteUser`): только администратор; нельзя менять себя и других админов; повторяющийся пароль отклоняется; отключение и смена пароля завершают открытые сессии.
- **Локально:** SHA-256 с солью в `localStorage` — только для демо, защиты нет.
- **Первый администратор:** `npx convex run authNode:seedAdmin '{"name":"Администратор","password":"…"}'`. Демо-каталог: `npx convex run data:loadDemoCatalog` (вставляет каталог, комплекты и клиентов, только если таблицы пусты).

## Маршруты (`src/App.tsx`)

`/` обзор · `/orders` · `/calendar` · `/events` · `/events/new` · `/events/:id` · `/events/:id/edit` · `/events/:id/estimate` (вне оболочки, для печати) · `/catalog` · `/clients` · `/users` (только админ).

Дерево: `AuthProvider` → `Gate` (загрузка / `Login` / `StoreProvider key={user.id}` → `Shell`).

## Страницы и компоненты — на что обратить внимание

- **EventWizard** (самый большой файл). 6 шагов, переход между ними **свободный**; обязательные поля проверяются только при сохранении. Все шаги с позициями остаются в DOM и только скрываются (`hidden`), чтобы поиск и вкладки не сбрасывались. Черновик хранится в `sessionStorage` (`luma-wizard:<id или new:<order>>`) и очищается при сохранении и «Отмене». Раскладка адаптивная: смета справа при ширине ≥ 1280 px, иначе под списком.
- **ItemGallery** — карточки с фото для блюд, мебели, посуды (`ItemCard`) и комплектов (`KitCard`); услуги остаются списком (`ItemPicker` внутри `EventWizard.tsx`).
- **Calendar** — месяц, занятость склада по дням (подсветка ≥ 80 % и ≥ 100 %), панель выбранного дня. Менеджер видит свои мероприятия, но занятость — по всем.
- **Estimate** — печатная смета; «Сохранить PDF» = `window.print()` + стили в `index.css` (`.no-print`, `@page`). Отдельного PDF-файла нет.
- **ReturnActDialog** — акт; для недостающего позиция требует причину.
- Картинки хранятся как data URL внутри записей (сжимаются до ~800 px, `image.ts`). Лимит документа Convex — 1 МБ.

## Convex (`convex/`)

- Таблицы: `catalog, kits, clients, events, orders` (прикладные), `users, sessions, loginAttempts` (вход). У прикладных строк строковое поле `id` (его использует интерфейс) и индекс `by_appId`; служебные `_id`/`_creationTime` перед отдачей клиенту убираются (`strip`). Имя индекса `by_id` в Convex зарезервировано.
- **Права и склад проверяются на сервере**, в тех же транзакциях, что и запись: `saveEvent` считает нехватку (`shortagesFor` из `src/lib/format.ts`) и отклоняет подтверждение, если позиций не хватает — два менеджера не займут одно и то же. Автор мероприятия проставляется сервером и не меняется. `applyReturnAct` атомарно закрывает мероприятие и списывает со склада; повторно не применяется.
- Права: каталог и комплекты пишет директор/админ; клиентов добавляют все, меняют директор/админ; заявки — все; мероприятия — автор, директор, админ; сотрудники — админ.
- Пользовательские ошибки бросаются как `ConvexError(текст)`; клиент показывает этот текст (`explain` в `backend/convex.ts`).
- Из `convex/` импортируются `src/lib/format.ts` и `src/lib/seed.ts` — они не должны зависеть от браузерных API.
- `convex/_generated/` коммитится. `tsconfig.app.json` подключает типы `node`, потому что `authNode.ts` попадает в типы `api`.
- Автотест серверной логики был одноразовым скриптом (не в репозитории): вход, права всех ролей, нехватка склада, акт возврата, перебор пароля, отключение пользователей. Стоит превратить его в `convex-test`.

## Известные ограничения и долги

1. **Production-деплой Convex не создан.** Сейчас всё на dev-деплое (`avid-ladybug-515`). Для боя: создать production-деплой, `npx convex deploy`, задать там `PASSWORD_PEPPER`, выполнить `seedAdmin`, прописать `VITE_CONVEX_URL` в Vercel (Settings → Environment Variables) и пересобрать. Пока переменной нет, публичная демо работает локальным режимом.
2. Пароль администратора, созданный для dev-деплоя, нужно заменить на боевой; смена пароля админа через интерфейс запрещена (только `npx convex run`).
3. Склад не учитывает время суток, только даты. Нет журнала движений, нет отметки «выдано / вернулось» кроме итогового акта. Акт нельзя исправить после подписания.
4. Фото хранятся как data URL внутри документов (лимит документа Convex — 1 МБ; фото сжимаются до ~800 px). Для большого каталога перейти на Convex File Storage.
5. Каждый снимок отдаёт все коллекции целиком. Для каталога в сотни позиций нормально; при росте разбить на отдельные запросы.
6. Нет автоматических тестов в репозитории.
7. Предупреждения линтера (`only-export-components`, `set-state-in-effect`, чтение ref в рендере) — стилистические.
8. `vite.config.ts` содержит `optimizeDeps.force: true` — костыль от устаревшего кэша зависимостей в dev; можно убрать.
9. Демо-пароли лежат в `README.md` и `local.ts`; при переходе на Convex-only их можно убрать вместе с локальным режимом.

## Идеи, которые обсуждали с владельцем (не сделаны)

- Публичная ссылка на меню для клиента (клиент сам выбирает блюда, итог уходит менеджеру) — требует отдельной публичной функции Convex без токена.
- Технологические карты кухни и список закупок — владелец отложил («потом добавим»).
- Журнал событий (кто и когда что менял), поиск по Cmd+K, дубль мероприятия, шаблоны писем, учёт оплат по частям.

## Соглашения

- Только компоненты Astryx для разметки (`VStack`, `HStack`, `Grid`, `Card`…), без `<div>` для раскладки и без `style={{}}`. Исключения — служебные `div` в печатной смете и скрытые обёртки шагов.
- Свойства Astryx отличаются от привычных: `isDisabled`, `isRequired`, `value` для `Switch`, `onChange` у `Selector` отдаёт строку. Перед использованием компонента читать типы в `node_modules/@astryxdesign/core/dist/<Компонент>/*.d.ts` или `node node_modules/@astryxdesign/cli/clients/cli/bin/astryx.mjs component <Имя>`.
- Новые права добавлять в `permissions.ts` и **одновременно** в серверные функции `convex/data.ts` — серверная проверка главная.
- Ключ `localStorage` версионируется (`luma-catering-crm-v5` в `local.ts`); при смене формы данных поднимать версию, иначе старые данные в браузерах сломаются.
- Все суммы считать через `eventTotals` / `kitPrice`, склад — через `freeStock` / `reservedOnDay` / `shortagesFor`.

## Проверенные сценарии (вручную, демо-режим)

Convex: 36 серверных проверок (права, склад, акт, перебор пароля) · запись клиента из интерфейса попадает в базу · вход настоящим паролем администратора · Демо-режим: вход неверным и верным паролем · менеджер видит только свои мероприятия и не открывает чужое по ссылке · `/users` закрыт для менеджера · каталог для менеджера без кнопок правки · админ создаёт сотрудника, дубль и короткий пароль отклоняются, новый сотрудник входит · директор видит все мероприятия с колонкой «Менеджер» · комплект ×2 раскладывается на позиции, «Ещё можно» уменьшается · блокировка подтверждения при нехватке · остаток возвращается после даты окончания · акт возврата списывает со склада · смета открывается и печатается · календарь показывает чужую занятость менеджеру · прод-сайт открывается, прямые адреса не дают 404.
